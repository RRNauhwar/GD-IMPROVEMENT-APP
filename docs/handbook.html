1 Executive Summary

SpeakX AI (repository GD-IMPROVEMENT-APP) is a browser-based coaching application that listens to a person speaking on a discussion/debate/interview topic and returns a structured, multi-dimensional coaching report: scores across 13 speaking dimensions, grammar corrections, fluency metrics (words-per-minute, filler words), speech-structure detection, personalized drills, gamification (XP, levels, streaks, badges), and a progress dashboard that charts improvement across sessions.

1.1 What problem does it solve?

Improving spoken English, group-discussion (GD) and interview performance normally requires a human coach who is expensive, not always available, and inconsistent. SpeakX AI provides an always-available, private, objective-first practice loop: pick a topic → speak against a timer → receive an immediate, measurable report → practice the auto-generated "next challenge" that targets your weakest dimension.

The central engineering idea. The product deliberately separates objective, deterministic analysis (computed locally in src/lib/analysis/engine.ts — WPM, filler counts, vocabulary diversity, rule-based grammar, structure detection) from an optional, subjective LLM narrative (src/lib/llm.ts). The app is fully functional and honest with zero external dependencies at runtime; the LLM only layers qualitative prose on top.

1.3 Business use case & why it exists

  • Positioning: a "practice-and-measure" tool that can be shipped as a free web app, embedded in ed-tech platforms, or upsold with the AI layer (bring-your-own-key today, managed key later).
  • Cost profile: because scoring is deterministic and client-side, the marginal cost per session is essentially zero unless the optional LLM is enabled. This is a genuine differentiator versus fully-LLM competitors.
  • Privacy: all data (sessions, progress, key) lives in the user's browser localStorage; nothing is transmitted unless the user opts into the OpenAI call.

1.4 Current limitations HONEST

  • Pronunciation & pauses are estimated from text, not audio. analyzePronunciation() flags long/known-hard words; longPauses is derived from WPM, not from the audio signal. This is explicitly labelled in the UI (PronunciationAnalysis.note).
  • Grammar is rule-based (10 regex rules) in grammar.ts — it catches common patterns (e.g. "should of", "he don't") but is not a full parser.
  • Transcription depends on the Web Speech API (Chrome/Edge). Other browsers fall back to a typed transcript.
  • No accounts / no cloud sync. Clearing browser storage erases all history.
  • No backend, database, authentication, tests, or CI/CD. NOT PRESENT

1.5 Future improvements (roadmap)

  1. Real audio analysis (Web Audio API + a speech model) for true pronunciation, pace and pause detection.
  2. A thin backend proxy so the LLM key is never in the browser (fixes the key-exposure risk in §12).
  3. Accounts + cloud persistence (Postgres/Supabase) for cross-device progress.
  4. Automated tests (Vitest + React Testing Library) around the pure engine.ts functions.
  5. Route-based code-splitting to shrink the ~610 kB bundle (Recharts dominates).

1.7 Interview pitch (2 minutes)

"GD-IMPROVEMENT-APP is a React 18 + TypeScript + Vite single-page app that coaches spoken English. The interesting engineering decision is the separation of concerns between measurement and opinion. I can walk through any of these, and I'm also happy to talk about what I'd add for production: a key-proxying backend, accounts, and tests."

4.2 Step-by-step narration

  1. Cold load. The static host returns index.html; Vite's hashed module bundle boots React. App's useState lazy initialisers call loadSessions()/loadGamification() so prior history is available on first paint.
  2. Setup. SetupScreen lets the user choose mode, difficulty, category, duration; generateTopic() produces a framed prompt. onStart lifts the config into App.active and switches screen to "speaking".
  3. Speaking. SpeakingScreen starts the timer and calls useSpeechRecognition.start(). The hook creates a SpeechRecognition instance, sets continuous+interimResults, and accumulates final chunks. A setInterval ticks the countdown; at ≤10s a warning shows; at 0 it auto-finishes.
  4. Finish & guard. onFinish computes countSpokenWords. If below MIN_SPEECH_WORDS (12), it routes to the "nospeech" screen and does not score/save/award — the fix that stops "marks for silence."
  5. Analyse. Otherwise analyzeSpeech() returns a fully-typed CoachReport. If a key exists, enhanceWithLlm() may add prose; failures fall back silently.
  6. Persist & reward. buildInsights() compares against history; awardForSession() updates XP/level/streak/badges and persists; saveSession() prepends the session.
  7. Render. screen="report" mounts ReportView; Recharts renders the radar; the user can jump to the "next challenge" or the dashboard.

5 System Design & Scaling

Framing. A client-only static SPA has an unusual scaling profile: the "server" is just a CDN serving immutable files, so raw traffic scales almost for free. The real scaling questions here are (a) the optional OpenAI dependency, (b) client-side storage limits, and (c) bundle delivery. I'll answer the classic sub-topics against this reality rather than pretend there's a fleet of app servers.

5.2 CAP theorem

CAP governs distributed data stores. Here, data is single-node (one browser's localStorage), so CAP barely applies: there is no partition between replicas because there are no replicas. If cloud sync were added, the honest choice for this domain (coaching history) is AP with eventual consistency — a user should always be able to record a session offline (availability) and sync later; a few seconds of staleness across devices is harmless. Strong consistency (CP) is unnecessary because there are no concurrent writers to the same record.

5.3 Database selection (if/when added)

OptionFit for this app
PostgreSQL (or Supabase)Best default. Sessions are relational (user → sessions → report JSONB). Supabase also gives auth + row-level security cheaply.
MongoDBViable — CoachReport is already a nested document; but relational reporting/aggregation is easier in SQL.
FirebaseFast to ship, good offline sync, but vendor lock-in and awkward complex queries.
RedisOnly as a cache / rate-limit store in front of the proxy, not as the primary store.

5.4 Bottlenecks (today)

  1. Bundle size (~610 kB, Recharts-dominated). First-load latency on slow networks. Fix: dynamic import() for chart-heavy screens.
  2. localStorage ceiling (~5 MB). Each session stores the full CoachReport + transcript. Thousands of sessions could approach the limit; there is no pruning.
  3. OpenAI rate limits & latency (only when AI enabled) — a per-key concern today; a shared-proxy concern later.
  4. Web Speech API quality/availability varies by browser and is network-backed in Chrome.

The only component that needs classic horizontal scaling is the AI proxy I'd add to hide the key — and that's a stateless service, so it scales linearly behind a load balancer with Redis for rate-limiting and caching."

6.4 The custom hook (concurrency & the Chrome auto-stop problem)

Chrome's SpeechRecognition fires onend periodically even mid-speech. The hook keeps a shouldListenRef and restarts recognition on onend until the user stops — a small but real piece of event-loop/async reasoning:

rec.onend = () => {
  if (shouldListenRef.current) {
    try { rec.start(); } catch { /* ignore double-start */ }
  } else {
    setListening(false);
  }
};

10 Authentication & Authorization

No authentication or authorization exists. There is no JWT, OAuth, session, cookie, refresh/access token, password hashing, or role-based access control anywhere in the codebase. The app is single-user-per-browser and stores everything locally.

10.1 Why this is (currently) acceptable

Because there is no server and no shared data, there is no identity to authenticate and no resource to authorize access to. Each browser sees only its own localStorage. The one secret in play — the optional OpenAI key — is supplied and owned by the user themselves.

10.2 What each requested concept would be if accounts were added

ConceptDesign for this app
Password hashingNever store plaintext; use bcrypt/argon2 on a backend. (Better: delegate to Supabase Auth / OAuth and store none.)
Access token (JWT)Short-lived (~15 min), signed, sent as Authorization: Bearer; carries userId to scope /api/sessions.

OAuthGoogle/GitHub sign-in — lowest friction for students; no password to manage.

10.3 Security risks tied to the absence of auth

  • No data protection at rest: anyone with the device can read history via DevTools.
  • Key exposure: the OpenAI key sits in localStorage in plaintext and is attached to a browser request — see §12 for the full analysis and fix.
  • No abuse controls: without identity there is no per-user rate limiting on the (future) AI proxy.

Interview soundbite: "I didn't add auth because there's no server and no shared state — it would be security theatre. The moment I introduce cloud sync, the correct move is OAuth (Google) + short-lived JWT access tokens with an httpOnly refresh cookie, and row-level security so a user can only touch their own sessions."

11 AI Module

The AI module is src/lib/llm.ts. It is optional and additive: the deterministic engine always produces the report; the LLM only rewrites the qualitative prose.

11.1 How AI is used

  • Triggered in App.handleFinish only when a key exists and the transcript is non-empty.
  • enhanceWithLlm() sends topic, difficulty, duration, the engine's overall score/WPM/fillers, and the transcript.
  • The model returns JSON with five fields; applyEnhancement() merges detailedFeedback, strongIdeas, weakArguments, motivational, dailyChallenge into the report and flips llmEnhanced = true.

11.2 Prompt flow & prompt engineering

The system prompt (SPEAKX_SYSTEM_PROMPT) does three deliberate things:

  1. Role framing: "world-class communication coach", explicitly "NOT a grammar checker" — steers away from duplicating the deterministic engine.
  2. Division of labour: tells the model that objective metrics are already computed, so it should add human, specific judgement, not recompute numbers.
  3. Structured output: demands a strict JSON object; combined with the API's response_format: {type:"json_object"} (JSON mode), this makes parsing reliable.

12.1 Detailed findings & fixes

Finding 1 — API key exposure HIGH

When AI is enabled, the browser calls OpenAI directly with Authorization: Bearer <key>. The key is therefore present in client memory and visible in the Network tab / any injected script. The code itself acknowledges this (Settings warns the user), but the architecture cannot fully mitigate it.

Fix: introduce a backend proxy (/api/enhance) that holds the key as a server secret; the browser sends only the transcript. This also enables per-user rate-limiting and response caching. This is the single most important production change.

Finding 2 — Plaintext key at rest MEDIUM

saveApiKey writes the raw string to localStorage, readable by any script on the origin (so it compounds with any XSS). Fix: once a proxy exists, don't store the provider key on the client at all; store only a session token for your own backend.

Finding 3 — Prompt injection LOW–MED

The transcript is untrusted and embedded in the user message. Blast radius is limited (JSON-mode output shown only to the same user; the app never executes model output). Fix: keep JSON mode, validate the parsed object against the expected shape (already partially done), and never feed model output into anything executable.

Finding 4 — Missing security headers MEDIUM

No CSP, X-Content-Type-Options, Referrer-Policy, etc. For a static SPA these are set at the host/CDN. Fix: add a strict CSP (allow self + api.openai.com for connect-src), X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin.

Findings 5 & 6 — Resilience LOW

Add a React Error Boundary; validate parsed localStorage with a schema (e.g. Zod) and migrate or discard invalid blobs instead of trusting them.

18.5 The Analysis Engine (domain deep-dive)

Q20. How is WPM computed, and what's the edge case? Medium
Ideal: "wpm = round(totalWords / minutes) where minutes = max(durationSec/60, 1/60). The max avoids divide-by-zero for a sub-second duration. It uses actualSpeakingSec, not the target, so a user who finishes early isn't penalised on pace."
Follow-up: Why actual vs target seconds?
Q21. How are filler words detected, including multi-word ones? Medium
Ideal: "Single-word fillers: tokenise, then membership-test against a Set (O(1) lookups). Multi-word phrases ('you know', 'i mean'): build a whitespace-tolerant regex per phrase and count matches on the raw lowercased text. Results are merged into one count map and sorted."
Follow-up: Why a Set for single words but regex for phrases?
Q22. How is vocabulary diversity measured? Medium
Ideal: "Type-token ratio: uniqueWords / totalWords using a Set for the numerator. Higher ratio = less repetition. It also finds overused words (count ≥ 3), flags weak words with upgrade suggestions, and detects 'advanced' words used."
Follow-up (trap): Isn't TTR biased by length? (Yes — short samples score higher; a real system would use MTLD/moving-average TTR.)
Q23. Explain the grammar checker design. Why regex and not an NLP parser? Hard
Ideal: "It's a Strategy list: an array of {test, fix, explanation, rule, difficulty} rules applied per sentence. Regex was chosen for zero dependencies, determinism, speed, and offline use. Follow-ups: How do you avoid duplicate issues? (a seen Set keyed by rule+sentence) How do you extend it? (append a rule object — open/closed)
Q24. How does structure detection work and what's its weakness? Medium
Ideal: "Discourse-marker lexicons (intro/argument/example/counter/conclusion) are substring-matched against the lowercased transcript; presence of each contributes to a 0–100 structure score. Weakness: marker-presence is a proxy — a well-structured speech that avoids explicit markers could score lower. It's a pragmatic heuristic, and I'd label it as such."
Q25. Walk me through the scoring for confidence. Why did empty speech used to score high? Hard
Ideal: "confidence = clamp(92 - fearSignals*12 - fillerRate*150 - repetitionRatio*20). 18.6 Data Structures, Algorithms & Complexity

Q28. What data structures does the engine use and why? Medium
Ideal: "Set for O(1) filler membership and for de-duplication (unique words, seen grammar issues); Map for word-frequency counting (countBy) and filler tallies; arrays for ordered lists and sorting. The choices are driven by the operation: membership → Set, counting → Map, ordering → array."
Q29. What's the time complexity of analyzeSpeech? Medium
Ideal: "O(n) in transcript length. Tokenising is one pass; frequency counting is O(w); grammar is 10 (constant) rules × sentences; structure markers are a constant set of substring scans; scoring is O(1) over 13 fixed dimensions. Space is O(w) for the maps/sets."
Follow-up: Any hidden quadratics? (The per-phrase regex and per-marker includes are constant-count × n, so still linear.)
Q30. How does the level-up loop work and could it be O(1)? Hard
Ideal: "while (xp >= level*100) { xp -= level*100; level++ }. It's a loop but bounded by how many levels a single session's XP can cross (tiny), so effectively O(1). With a closed-form threshold you could compute the target level directly, but the loop is clearer and cheap."
Q31. Explain the syllable estimator. Is it exact? Hard
Ideal: "It strips silent endings ('e', 'es', 'ed'), removes a leading 'y', then counts vowel groups via regex, min 1. It's a well-known heuristic — fast and dependency-free but not exact (English is irregular). It's only used to flag 'likely hard to pronounce' long words, so approximate is fine."

function topRepeated(text: string, n = 3) {
  const counts = new Map<string, number>();
  for (const w of text.toLowerCase().match(/[a-z']+/g) ?? []) {
    if (w.length > 3) counts.set(w, (counts.get(w) ?? 0) + 1);
  }
  return [...counts.entries()]
    .sort((a, b) => b[1] - a[1])
    .slice(0, n)
    .map(([word, count]) => ({ word, count }));
}

interface Rule { test: RegExp; fix: (s: string) => string; rule: string; }
const RULES: Rule[] = [
  { test: /\b(should|could|would)\s+of\b/i,
    fix: s => s.replace(/\b(should|could|would)\s+of\b/gi, "$1 have"),
    rule: "Modal + have" },
];
function check(text: string) {
  const out: {original:string; corrected:string; rule:string}[] = [];
  for (const s of text.split(/(?<=[.!?])\s+/)) {
    for (const r of RULES) {
      if (r.test.test(s)) {
        const corrected = r.fix(s);
        if (corrected.toLowerCase() !== s.toLowerCase())
          out.push({ original: s, corrected, rule: r.rule });
      }
    }
  }
  return out;
}
